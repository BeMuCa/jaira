- Look for a milestone in `.jaira/milestones/<name>-<ID>.md`, on `refs/jaira/milestones/<ID>`, and in `milestone ls --json` as `id`: the six upper-case characters after the last dash are what a milestone is, the name before them is only its label, so `jaira milestone rename` (and `e` on the Milestone Roadmap) changes the file name on the same ref and nothing else.
- Give `jaira milestone add`, `rm`, `set`, `rename`, `jaira logbook` and `jaira list --milestone` a milestone by name, ID or `<name>-<ID>`; for the five that write, a name two milestones carry exits 3 with both `<name>-<ID>` forms to run again with, and writes nothing, while `jaira list --milestone <name>` is a filter and shows the tickets of every milestone with that name (exit 0), so give it the `<name>-<ID>` or the ID to narrow it to one.
- Expect milestones in the board filter, the `M` picker, the roadmap and `jaira milestone ls` by name alone, and as `<name>-<ID>` only where two share a name; a tick on one of them filters just that one.
- Update the whole team together: the automatic background fetch of this build usually moves every old `<name>.md` to `<name>-<ID>.md` silently, and only a foreground `jaira fetch` or a milestone command that writes prints the move (`jaira fetch --json`: `milestones_migrated`; `jaira milestone ls` moves nothing), so look in `.jaira/milestones/` if a name changed; the ID is computed from the old name so every clone agrees without talking, the old name refs stay on the remote, and a 0.4.x build stops seeing what this build does to a milestone from then on, so nobody keeps working on 0.4.x.
- Expect an edit a 0.4.x teammate made to a milestone, before or after your clone moved it to its ID, to be merged in and not dropped: the milestone command that moves old files fetches first when the remote is reachable (offline it moves anyway and merges at the next fetch), and a fetch then merges what a 0.4.x build wrote to the old name ref or an old `<name>.md` since — tickets it added or removed, a goal, `after:` (names become IDs) or any other field only it changed; a field you changed too keeps your value, and the 0.4.x value is printed on stderr and by `jaira fetch` (`--json`: `milestones_conflicts`) and written into the milestone file as a `<!--` comment, so look there if a 0.4.x teammate edited the same line.
- Write `after:` as milestone IDs: jaira now writes IDs, reads a name only for a hand-written line, and spells a name as its ID the next time it writes that file, so renaming a milestone no longer touches the milestones that follow it.
- Create a milestone under the name of a filed one when you need to (changes 0.4.x, which kept a filed name taken): a filed milestone no longer holds its name, and a `jaira restore` next to a milestone of the same name leaves both, told apart by their IDs; `jaira logbook` no longer says the name stays taken.
- Never run a 0.4.x build and this one on the same clone: what the 0.4.x build writes there lands on the old name ref and in an old `<name>.md`, and this build merges it into the ID milestone on its next fetch or milestone write (see the line above), so nothing is lost; but on macOS and Windows the 0.4.x CLI lower-cases the file name, so its edit turns up as a second milestone `<name>-<id>` in lower case beside the real one, and you make that edit again on the real one with this build.
