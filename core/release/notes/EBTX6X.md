- Look for a milestone in `.jaira/milestones/<name>-<ID>.md`, on `refs/jaira/milestones/<ID>`, and in `milestone ls --json` as `id`: the six upper-case characters after the last dash are what a milestone is, the name before them is only its label, so `jaira milestone rename` (and `e` on the Milestone Roadmap) changes the file name on the same ref and nothing else.
- Give `jaira milestone add`, `rm`, `set`, `rename`, `jaira logbook` and `jaira list --milestone` a milestone by name, ID or `<name>-<ID>`; a name two milestones carry exits 3 with both `<name>-<ID>` forms to run again with, and writes nothing.
- Expect milestones in the board filter, the `M` picker, the roadmap and `jaira milestone ls` by name alone, and as `<name>-<ID>` only where two share a name; a tick on one of them filters just that one.
- Update the whole team together: the first milestone command or foreground `jaira fetch` of this build moves every old `<name>.md` to `<name>-<ID>.md` and prints the move (`jaira fetch --json`: `milestones_migrated`), while the automatic background fetch moves them without saying so, so look in `.jaira/milestones/` if a name changed; the ID is computed from the old name so every clone agrees without talking, the old name refs stay on the remote and are ignored once the ID ref is there, a 0.4.x build stops seeing milestone changes from then on, and an edit a 0.4.x teammate makes on the old name after your clone migrated is not picked up, so nobody keeps working on 0.4.x; an edit such a teammate made before you migrated but your clone had not fetched yet is lost too when your first milestone command runs before any fetch of this build, because that write migrates your stale local copy and its ID ref wins, so run `jaira fetch` once after updating, before your first milestone command (a background fetch that already ran does the same).
- Write `after:` as milestone IDs: jaira now writes IDs, reads a name only for a hand-written line, and spells a name as its ID the next time it writes that file, so renaming a milestone no longer touches the milestones that follow it.
- Create a milestone under the name of a filed one when you need to (changes 0.4.x, which kept a filed name taken): a filed milestone no longer holds its name, and a `jaira restore` next to a milestone of the same name leaves both, told apart by their IDs; `jaira logbook` no longer says the name stays taken.
- Update every build on a clone together, never run a 0.4.x build and this one on the same clone: a milestone edit the 0.4.x build makes there is queued under the old key and, once the milestone's ID ref is on the remote, is refused as "someone else wrote it first" and lost, or, on macOS and Windows through the 0.4.x CLI, turns up as a second milestone `<name>-<id>` in lower case beside the real one; either way make that edit again with this build.
