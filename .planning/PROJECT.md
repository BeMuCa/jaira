# jAIra

## What This Is

A lightweight, git-synced kanban board for the tasks Claude Code generates while working in a repo. Tickets are markdown files committed inside the repo, so the board travels with the code — a teammate clones, runs `jaira`, and sees the same state with no server, no accounts, and no setup. Each lane is a configurable agent step (prompt + model tier + input/output contract), which turns the board from a tracker into a visible, resumable agent pipeline.

## Core Value

**You never lose track of what a task was for or where it stands** — across session boundaries, agent runs, and teammates.

Everything else is negotiable. If the board can't answer "what was this ticket supposed to do, why, and what state is it in?" months later, it has failed.

### Active

**Ticket store**
- [ ] Tickets are markdown files with YAML frontmatter under `.jaira/tickets/`, one file per ticket
- [ ] Board state survives session death — close Claude, reopen the repo, tickets and lane positions are intact
- [ ] A teammate who clones the repo and runs `jaira` sees the same board with zero configuration
- [ ] Ticket carries: `id`, `title`, `status`, `goal`, `context`, `blocked-by`, `definition-of-done`, `creator`, `assignee`, `model-tier`, outcome (`what` / `why` / `resolves`), `commits[]`
- [ ] Frontmatter reserves an `external:` block so a Jira/YouTrack adapter can be added without migrating existing tickets

**Board / TUI**
- [ ] Terminal TUI renders the board as lanes with keyboard navigation
- [ ] Seven base lanes ship with the tool and require no repo config: Backlog, Todo, In Progress, Human, Review, Done, Blocked
- [ ] Pressing a key on a card expands the full ticket detail inline
- [ ] Cards can be created and thrown into the Backlog directly from the TUI
- [ ] Lanes the local install doesn't know about render as read-only passthrough columns, so tickets are never hidden
- [ ] Session panel shows the current focus and reasoning, written by Claude via CLI at checkpoints
- [ ] Switching between projects from within the TUI

**Capture and the promotion gate**
- [ ] Claude's TodoWrite items are mirrored into the Backlog as tickets with `ready: false`
- [ ] TodoWrite sync is two-way — starting a ticket populates the in-session checklist, so the flow that begins in chat ("fix the bugs that were found") stays visible in both places
- [ ] Duplicate suppression: repeated TodoWrite calls update existing tickets instead of creating new ones
- [ ] A ticket cannot leave the Backlog until `goal`, `definition-of-done`, `context`, and `assignee` are all present
- [ ] `context` can be auto-generated by Claude from the conversation that spawned the ticket
- [ ] `assignee` defaults to the ticket's creator and can be reassigned to any teammate
- [ ] Work is always attributed to a human; the model that executed a run is recorded separately as `executed-by`

**Dependencies**
- [ ] A ticket declares `blocked-by` referencing other tickets
- [ ] A ticket with unsatisfied dependencies cannot be started

**Agent pipeline**
- [ ] Custom lanes are single portable markdown files in `~/.jaira/lanes/`, shareable by sending the file
- [ ] A lane definition specifies its prompt, its model tier, and its input/output contract
- [ ] Claude Code works the board in-session, spawning a subagent per lane step at that lane's model tier
- [ ] Agents advance tickets through lanes as work completes
- [ ] A ticket needing user input lands in the Human lane with the question attached
- [ ] Each completed ticket ends with a concise outcome: what was done, why it was needed, and how the change satisfies the Definition of Done
- [ ] Commits produced for a ticket are recorded on it, and the combined diff is viewable from the board

**Interface**
- [ ] A CLI is the single write path — TUI, Claude, and any future integration all go through one schema enforcer
- [ ] The CLI is drivable by any agent that can run bash, not just Claude Code
- [ ] A skill teaches Claude the CLI and the ticket schema
- [ ] Distributed as a single static binary with no runtime dependency
- [ ] Instant startup

### Out of Scope

- **Sprints, custom fields, roles/permissions, saved views, dashboards** — paca already does this and was too big; the entire point is a smaller surface
- **Server, accounts, authentication** — git is the sync layer; adding a server would reintroduce the weight being escaped
- **Jira / YouTrack / external sync** — deferred to v2, but the schema reserves space for it so no migration is needed later
- **Web UI and VS Code extension** — TUI-first; a shared board is achieved through git, not through hosting
- **Branch per ticket** — too heavy for small tasks and awkward when multiple agents work in parallel
- **Board-spawned headless `claude -p`** — orchestration lives in the session instead, avoiding background processes to manage
- **TodoWrite as the backbone** — it is a capture on-ramp only; todos lack the DoD, context, and dependencies that make a ticket useful, which is exactly what the promotion gate supplies

## Context

**Origin.** Handing Claude Code a single task reliably explodes it into sub-tasks — "first task, second task, third task". Within a session that is fine. Across sessions it is not: the purpose of each sub-task and its state both evaporate, and there is no artifact left to reconstruct them from. jAIra exists to make that state durable and visible.

**Relationship to paca.** A paca MCP server is already available in this environment and covers the same problem space with projects, tasks, sprints, statuses, views, custom fields, and automations. It was judged too big. jAIra is a deliberate reduction: local files instead of a server, git instead of accounts, seven lanes instead of a configurable workflow engine. Feature parity with paca is an anti-goal.

**Secondary goal — quality per token.** Lanes are not only a progress display. Because each lane binds a prompt, a model tier, and an I/O contract, the board doubles as a way to get code produced cheaply and checked expensively: a low-tier model implements, a strong model critiques. The value is a controlled, inspectable pipeline rather than one large opaque agent run.

**Review ergonomics.** The reviewer's question is never only "what changed" but "why does this change resolve the task". The outcome block is therefore three fields, not two: the problem, the change, and the causal link to the Definition of Done — enough to review without opening the code.

**Multi-user model.** Team sharing is a consequence of the storage choice rather than a feature. Because tickets are committed files, collaboration comes free — and so do merge conflicts. Two people moving the same ticket collide on one frontmatter line, which makes conflict tolerance a first-class design constraint rather than a later fix.

**Environment.** Development happens on Linux (WSL2). Node 24 is available. The repo is currently empty — greenfield, no existing code to accommodate.

## Constraints

- **Tech stack**: Single static binary, Go or Rust — no runtime dependency, because every teammate must be able to install and run it trivially
- **Storage**: Markdown with frontmatter, inside the repo — the file format *is* the API, and must stay hand-editable and diff-readable
- **Sync**: Git only — no server, so any feature requiring central coordination is off the table by construction
- **Performance**: Instant startup — the board is glanced at constantly, and a slow board will not be opened
- **Compatibility**: CLI must be usable by any bash-capable agent, not only Claude Code
- **Concurrency**: Multiple parallel Claude sessions and multiple teammates write the same store, so the format must minimize and survive conflicts
- **Scope discipline**: Every feature is measured against "is this smaller than paca?" — the project fails by growing

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Git is the sync layer; no server | Delivers multi-user for free and keeps the tool installable in seconds | — Pending |
| Tickets are markdown files in `.jaira/tickets/` | Hand-editable, diff-readable, git-mergeable; the format doubles as the API | — Pending |
| CLI is the single write path, with a skill teaching Claude | One schema enforcer prevents TUI and agent drift; works with any bash-capable agent; MCP can wrap it later | — Pending |
| Terminal TUI rather than web or editor extension | Matches "very lightweight, very fast"; sharing is solved by git, so no host is needed | — Pending |
| Seven base lanes ship built-in, not as repo config | A teammate's board works immediately without inheriting anyone's workflow | — Pending |
| Custom lanes are portable single files in `~/.jaira/lanes/` | Reuse across projects, and sharing is just sending a file | — Pending |
| Unknown lanes degrade to read-only passthrough columns | Hiding tickets is a worse failure than showing an inert column | — Pending |
| Lanes bind a prompt, a model tier, and an I/O contract | Turns the board into a controlled pipeline: cheap implementation, expensive review | — Pending |
| Claude spawns subagents in-session; the board does not spawn agents | Avoids background process management, keeping the tool a queue plus a view | — Pending |
| TodoWrite mirrors into the Backlog behind a promotion gate | Zero-friction capture, while making a Definition of Done the price of entering execution | — Pending |
| TodoWrite sync is two-way | Ticket flow starts in chat, so the in-session checklist and the board should not diverge | — Pending |
| Attribution is always human; `executed-by` records the model | Ownership of outcomes stays with people even when agents do the work | — Pending |
| External sync deferred to v2, schema reserved now | Auth, field mapping, and conflict resolution would exceed the board itself in effort | — Pending |
