# Quick Task: `f` overrides a refused move, on the page you are already on

## The report

Moving a ticket from review to done was refused because the assignee (an email
address) did not read as the user. The TUI's answer was "use the CLI with
--force" — leave the board, retype the move. Wanted instead: the refusal says
`f` overrides, `f` asks once more, and the whole thing happens without leaving
the page.

## Established facts (read in the code this session — do not re-investigate)

- The refusal comes from `gate.CheckAdvance` → `CodeNotOwner`
  (`core/gate/gate.go:159-173`). Its message already ends "or override with
  --force". **`core/gate` is shared with the CLI and is not touched by this
  task.**
- `applyMove()` (`internal/tui/model.go:961-1015`) is the TUI's move. It claims
  an unassigned ticket first (`me` = `identity.Current`), runs the gate, and on
  refusal calls `notify(...)` with "Edit the ticket to supply what is missing, or
  use the CLI with --force."
- `CheckAdvance` has **no** force parameter. The CLI's `--force`
  (`internal/cli/flow.go:171`) simply does not return the refusal:
  `if len(vs) > 0 && !force { return ... }`, then runs the same mutation
  (`flow.go:186-191` — `FieldStatus` + `ticket.SetReady`) and prints "Overrode N
  gate refusal(s)" (`flow.go:203-205`). Nothing is written to the ticket to
  record the override. The TUI's force must therefore be exactly: skip the
  refusal, same mutation, say what it overrode.
- `applyMove`'s own mutation (`model.go:995-1006`) already matches the CLI's,
  plus the claim.
- **Every overlay dismisses to the board, whatever it was opened from:**
  `case modeHelp, modeMessage` → `m.mode = modeBoard` (`model.go:704-708`),
  `modeMove`'s esc/q → `modeBoard` (`model.go:679-680`), `applyMove`'s success
  path → `modeBoard` (`model.go:1010`). So a refusal raised from lane focus or
  from an open ticket already loses the page. Forcing "on the same page" is not
  possible without fixing this first.
- `openMove()` is reachable from the board (`model.go:896-897`) and from an open
  ticket (`model.go:795-796`). Lane focus has no `m` (`lanefocus.go:15-41`).
- `f` in `modeDetail` is **already taken**: follow-up at a human checkpoint
  (`model.go:786-789`). `modeMessage` binds no keys at all beyond dismiss
  (`model.go:705`), so `f` is free there and only there.
- `renderMessage()` (`view.go:784-796`) footer is the fixed string
  `"esc dismiss"`.
- `mode`'s zero value is `modeBoard` (`model.go:33`, iota), so an unset
  return-to field means today's behaviour.
- `switchBoard()` (`model.go:170-192`) resets per-board view state by hand.
- `holdsLane()` / `holdLane()` (added by quick 260819-p3m) resolve `modeDetail`
  through `m.detailFrom`; overlay modes were deliberately left out of that pass.
- Baseline green: `go build ./...`, `go test ./... -race`, `gofmt -l internal/tui/`
  empty.

    - Dismissing the refusal without pressing `f` → nothing moved, and `f`
      afterwards does nothing (no stale offer).
    - Force covers every refusal code, not just ownership: a move refused for a
      missing definition of done is forceable too, exactly as `--force` is.
    - `renderMessage()` shows `f override · esc dismiss` while a force is on
      offer, `y override · n cancel` while confirming, and plain `esc dismiss`
      otherwise.

    whether the move also claims the ticket, the refusals, and whether `f` has
    already been pressed. Keep it on the model as `pending *pendingMove`.
    Comment it as what it is: the refused move, kept so the notice can offer to

    override.

    `switchBoard()` clears `m.pending`: it names a ticket in the store being

## Constraints

- `core/gate` and `internal/cli` are not touched. Force stays a TUI affordance
  over the existing, unchanged gate.
- No new field on the ticket file: the CLI's `--force` records nothing, and the
  TUI must not invent an audit trail the CLI does not write.
- `modeHelp` keeps dismissing to the board.
- No third confirmation, no "are you sure" on the `n` path.
