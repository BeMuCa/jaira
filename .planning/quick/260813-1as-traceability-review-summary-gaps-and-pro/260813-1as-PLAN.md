<objective>
Make it possible to follow what a change actually did.

Two halves, both about the same failure: a ticket that passed review but leaves
no trace of what was done or whether anyone checked it.

1. The review lane gains `review-summary` (what the change does, from the diff,
   in plain language) and `review-gaps` (what the reviewer found missing — "none"
   is a valid answer, empty is not). Both are declared in the lane's
   `output-produces`, which the gate already enforces, so review cannot be
   passed through silently.
2. Every definition-of-done item can carry a `proof:` sub-line naming the
   evidence, written in the same call that ticks the item.

Purpose: an empty review field must always mean "nobody looked", never "nothing
found"; and a ticked box must be able to say why it is ticked.
Output: two new frontmatter fields end to end, a proof sub-line format with a
writer/parser/CLI flag/JSON field, and the prompts and rendering that make both
get used and get read.
</objective>

Note, against the brief: `review-verdict` is **not** in `canonicalOrder`
(`schema.go:58-66` — check it). `canonicalOrder` only shapes files jaira creates
from scratch, and a brand-new ticket has no review output. Do not add the two new

`jaira set <id> field=value` (`internal/cli/tickets.go:521`) writes any scalar
generically via `Doc().SetScalar`, and multi-line values already round-trip
(`core/ticket/multiline_test.go`). So the reviewer agent needs no new CLI command
to write these two fields — do not add one.

`ticketJSON` (`internal/cli/tickets.go:687`) does not expose `review-verdict`
today. Keep the two new fields out of it for the same reason: they are read by a
person on the sign-off screen, not branched on by an agent. Proof is different —
it is explicitly requested in `--json`.

The gate's output-produces enforcement, which is what makes the new fields
mandatory without any new gate code:

The checklist parser, which already ignores a non-checkbox indented line:

```go
// core/ticket/schema.go:220-246 (abridged)

```

`parseCheckbox` (`schema.go:251`) only accepts `- `/`* `/`+ ` followed by `[x] `.
A line reading `  proof: ...` is therefore already dropped on the floor today —
which is the whole reason this format was chosen.

`AddItem` (`checklist.go:125-140`) inserts a new checkbox at `idx[len(idx)-1] + 1`,
i.e. **the line directly after the last item** — which is exactly where that
item's proof line will now sit. This is the one place the new format collides
with existing behaviour, and Task 2 fixes it.

`SetItemState` (`checklist.go:52-74`) edits by line index and only swaps the
marker character, so it is indifferent to proof lines already.

**The format.** A proof is a non-checkbox, indented plain line directly under its
item: two spaces of indentation beyond the item's own, then `proof: ` then the
text. It must never be a bullet with a bracketed marker, or `checklistUnder`
would read it as another acceptance criterion — that is the one hard constraint
on this format. Define the prefix once as a package-level constant (e.g.
`proofPrefix = "proof:"`) in `core/ticket/checklist.go` and use it in both the
parser and the writer; two spellings of the same marker is how a format silently
stops round-tripping.

**Parser.** Add `Proof string` to `DoDItem` (`schema.go:166`). In `checklistUnder`,
after the `parseCheckbox` attempt fails, test whether the trimmed line
case-insensitively starts with the proof prefix and there is at least one item
parsed so far in this section; if so, assign the remainder (trimmed) to the last
item's `Proof` and continue. Last one wins if a hand-edited file somehow has two —
the writer guarantees one, and picking the later line is one branch instead of
two. Comment WHY the proof rides on the item rather than living in its own section.

**Writer.** Add to `core/ticket/checklist.go`:

    func SetItemProof(body string, sec Section, i int, proof string) (string, error)

`checklistLineIndexes` for the item's line number and reuse its two error cases
(no such checklist; no such item number). Collapse all whitespace runs in `proof`
to single spaces so a multi-line value cannot break the one-line sub-line model,
and reject an empty result the way `AddItem` rejects empty text. Derive the
indentation from the item line's own leading whitespace plus two spaces, so a
nested checklist keeps its shape. If the line immediately following the item is
already a proof line, replace it in place; otherwise insert. Leave the item's own
line completely untouched — the point of `SetItemState`'s one-character diff
applies here too.

**Fix `AddItem`.** Where it computes `at := idx[len(idx)-1] + 1`, advance past a

Whole-suite: `export PATH=$PATH:$HOME/.local/go/bin && go test ./... && go build ./...`

End-to-end, by hand in a scratch repo:
1. `jaira new` a ticket, take it to review with a commit recorded.
2. `jaira move <id> done` → refused, naming `review-summary`.
3. `jaira set <id> review-summary="..." review-gaps=none review-verdict="..."` → the move is allowed.
4. `jaira dod <id> 1 --done --proof "internal/x.go:12; TestX"`, then `jaira dod <id> 1 --proof "different"` → the file has one proof line, replaced.
5. `jaira dod <id> --add "another criterion"` → the new checkbox lands below the previous item's proof line.
6. `jaira show <id> --json | jq '.dod_items'` → each item carries `proof`.
</verification>
