# Summary: the loop, written down

Three things, all about making the flow legible rather than adding machinery.

## What was established first, in the code

- **Loops already worked.** The gate only checks a move that advances: `to > from`
  guards both the dependency check (`core/gate/gate.go:208`) and the leaving
  lane's output contract (`:362`). A backwards move is free. What was missing is
  that nothing *declared* where back was, so the route lived in a prompt's prose.
- **Built-ins are always injected.** `Load` starts from `Builtins()`
  (`core/lane/lane.go:399`), so a new built-in appears on every board. Two lanes
  the user explicitly did not want on the default board therefore could not be
  built-ins.
- **The drift warning only fires on same-id overrides.** `lanesEquivalent`
  (`core/lane/lane.go:527`) compares behaviour fields, so a new field left empty
  on both sides keeps a project copy equivalent. Adding `rejects-to` costs no
  warnings as long as no built-in declares one — which none does, asserted by a
  test.
- **TUI `R` cannot refresh a built-in.** `Drift` skips `l.Builtin` and needs a
  catalogue file to compare against (`core/lane/share.go:146-153`), so
  `jaira lanes use <id> --force` is the only refresh path for a built-in copy.
  This answered a direct question and is worth keeping: the TUI and the CLI are
  not interchangeable here.
- **jaira never commits.** `core/gitrepo` exposes only reads (`Commits`, `Diff`,
  `Stat`, `HeadSHA`, `IsRepo`, `Root`); the sole git write in the program is
  `git config --local` for the merge driver.

## f6015d1 — a lane declares where it sends work back to

`rejects-to:` names the loop's back edge. `checkContracts` warns if it does not
resolve to an installed lane, and if a lane names itself (a stall, not a loop).
`lanesEquivalent` counts a moved back edge as a changed lane. `lanes show` prints
it next to the anchor, `--json` carries `rejects_to`, the template documents it.

Documentation the tool validates, not a rail: nothing forces a rejection to go
where the field says.

## 9ea9a64 — critique and optimise, as catalogue lanes

`lanes/critique.md`, `lanes/optimise.md`, `lanes/README.md`. Both declare
`rejects-to: in-progress`.

- **critique** judges the approach, not whether it works, in four questions
  (simpler shape, fits what is here, speculative, right place). It does not fix
  anything itself: reviewing your own repair in the same breath is how a critique
  stops being one. A finding whose resolution is the user's call goes to HITL with
  the question rather than being decided by whichever agent noticed it.
- **optimise** does edit, in four passes with duplication first, because two
  implementations of one idea is the most expensive thing on the list. It stops if
  a cleanup would change behaviour.

`core/lane/shipped_test.go` loads everything in `lanes/` on every CI run — nothing
else does, since these are not embedded. It caught a real defect immediately: an
unquoted colon in optimise's description, which YAML read as a nested mapping and
which cost the lane its `id`.

## Installed on the user's board

`jaira lanes adopt lanes/critique.md` / `optimise.md` into the catalogue, then
`jaira lanes add` on the req board. Two observations worth recording:

- The board already had an active `.jaira/lanes/` (holding `review.md`), so
  `MaterialiseWorkingSet` returned early (`core/lane/order.go:170`) and **nothing
  was materialised**. Only the two new files appeared. The warning given before
  the install was therefore too pessimistic for this board.
- `lanes add` appends to the order file, which then overrides `after:` — so both
  lanes landed at the far right of the board. Removing the order file (it had just
  been created by the add) restored anchor ordering and put them where they
  belong: `Implementing → Critique → Optimise → … → Review`.
