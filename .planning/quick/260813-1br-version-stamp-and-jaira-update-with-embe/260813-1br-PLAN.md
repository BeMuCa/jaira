<objective>
A board remembers which jaira version last set it up. Every command notices when
the running binary is newer than that stamp and says so once, on stderr. `jaira
update` re-runs the idempotent board setup, prints the change notes between the
two versions from notes embedded in the binary, and writes the new stamp.

Purpose: the board setup (`.gitignore` entry, agent note in `AGENTS.md`/`CLAUDE.md`)
is written once at init and then silently rots as jaira changes. Today nothing
tells a user or an agent that the instructions they are reading are from an older
binary. This closes that gap without a server, a network call, or a committed file.

Output: a `core/release` package, a `jaira update` command, a one-line nudge in
`openStore`, and the first real change-note entry.
</objective>

<design_decisions>
These are settled. Implement them; do not re-open them.

**Where the stamp lives.** `<stateDir>/version`, a single line holding the exact
version string. `stateDir()` is the per-working-tree directory under `$JAIRA_HOME`
or `~/.jaira` (`core/ticket/store.go:158`); after `init` it already holds
`sessions/` and `locks/`, so the stamp lands beside them. Not `.jaira/` inside the
repo: on a shared board a committed version file would conflict on every teammate's
upgrade, and "which version have I run here" is a property of the clone, not of the
board.

**Note format.** `core/release/NOTES.md`, embedded with `go:embed`, newest release
first. A release is a line starting exactly `## ` followed by the version string a
build of that release reports (goreleaser stamps `{{.Version}}`, which is the git
tag with its leading `v` stripped — so the heading for tag `v0.1.0` is `## 0.1.0`).
Inside a release, every change is exactly one line starting `- `. One line per
change, no wrapping — the parser is a line scan, and wrapping would silently split
a change in two. Anything else in the file is ignored, so prose and HTML comments
are free.

**Selecting "between X and Y".** Selection is driven by the *stamp alone*, by
position in the file, with no semver parsing:
- stamp matches a heading → every entry *above* it, in file order.
- stamp is empty (unstamped board) → every entry.
- stamp matches nothing (a `dev` stamp, a goreleaser snapshot/nightly version, or a
  version older than the oldest entry) → every entry.
- stamp is the top entry → nothing.
This is unambiguous because it never has to reason about the running binary's
position in a history it may not appear in (a release can ship with no notes).
Showing too much on an unknown stamp is the safe direction; showing too little is not.

**The `dev` rule.** A binary reporting `dev` never nudges. A local build's version
string says nothing about what is in it, and nagging a developer on every
invocation of their own build is pure noise. `jaira update` still works fully on a
`dev` build: it re-runs Prepare, prints every entry (the `dev` stamp matches no
heading), and stamps `dev`. The next real release then differs from that stamp and
nudges once, which is correct.

The rule keys on the exact string `dev` and nothing else. Goreleaser rewrites
`.Version` for snapshot and nightly builds, so such a binary reports something like
`0.1.1-next` — it is not `dev`, so it nudges and shows every note. That is the
correct outcome for a prerelease and needs no extra handling; do not add pattern
matching for it.

**The nudge.** One plain line on stderr, printed regardless of `--json`, matching
`bindDriverIfShared` (`internal/cli/share.go:128`) — the same hook, the same class
of message ("this clone needs one-time setup"). It must never touch stdout: stdout
carries `--json` payloads an agent parses. If the state directory is unreadable the
nudge is silently skipped; a command must never fail because of it. `jaira update`
itself must not nudge — it is the fix.

**No network.** jaira never phones home. This is entirely local: binary version vs.
stamp on disk.
</design_decisions>

Exports:

  set once by `cli.Execute`, because the TUI creates boards too and plumbing a
  version string through the whole TUI to stamp one file is not worth it. Comment

never copied to disk anywhere — a copy can drift from the binary that reads it, and
the binary always knows what is in itself. Say that in the package doc comment.

the trimmed remainder. `strings.HasPrefix(line, "- ")` inside an entry appends the
trimmed remainder as a change. Everything else is skipped. Fewer than ~25 lines.

rules (newest release first; `## <exact version a build reports>`; one change per
`- ` line, never wrapped) so a future contributor cannot get the format wrong by
