# Quick Task: x deletes catalogue lane files, and every x asks first

## Root cause (already established — do not re-investigate)

Berk pressed `n` on the lane settings screen and closed the editor without
saving. `n` deliberately writes the skeleton **before** opening `$EDITOR`
(`writeLaneSkeleton`, `internal/tui/lanes.go` — design invariant: lanes are
files, not a form), so `~/.jaira/lanes/new-lane.md` with `id: my-lane` was left
behind. It now shows on the settings board as a dimmed "not on board" column
and **cannot be deleted from the TUI at all**:

- `x` calls `laneScreen.remove()` → `ls.selected()`, which returns nil for
  a lane that is only in `ls.available` → silent no-op.
- `core/lane.Remove` is board-only by design ("never the catalogue") and no
  other code path deletes a catalogue file.

## What to build (two things, both in `internal/tui/lanes.go` + tests)

### 1. `x` works on a not-installed catalogue lane: delete its file

- When the cursor sits on an installed lane → current behaviour
  (`lane.Remove`, board removal).
- When the cursor sits on an **available** (dimmed, "not on board") lane:
  - `l.Builtin` → error message, e.g. `built-in lane "<id>" lives inside the
    binary — nothing to delete` (a built-in has no file; do NOT delete it).
  - otherwise → delete `l.Source` with `os.Remove`, then `ls.reload()`, msg
    `deleted <path>`. Available lanes only come from builtins + the
    `UserLanesDir()` glob (see `core/lane/order.go` `Installable`), so
    `l.Source` is always a catalogue file here — no extra path guard needed.
- On the `+` column: `x` stays a no-op.

### 2. Every `x` asks first: yes/no confirmation, default No

Berk's spec, verbatim requirements:
- left/right (and h/l) switch between the two answers,
- **"no" is listed first AND selected by default**, so hammering enter never
  deletes anything,
- enter executes the selected answer, esc cancels.

Implementation shape (follow the existing style of the file — e.g. the
`confirmAdoptID` pattern and its comment style):

- New field on `laneScreen`: `confirm *confirmRemove` with
  `type confirmRemove struct { id string; path string; yes bool }` —
  `path` empty = board removal, non-empty = catalogue file delete. `yes`
  starts false.
- In `key()`, directly after the `catalogueOpen` block: when `ls.confirm !=
  nil`, intercept everything: `h`/`left` → `yes = false`; `l`/`right` →
  `yes = true`; `enter` → clear confirm, and if yes was selected run the
  removal (board via `lane.Remove` with the stored id, keeping the existing
  occupied-lane refusal and its message; catalogue via `os.Remove` + reload);
  `esc`/`q` → just clear confirm (must NOT close the screen). All other keys
  ignored. Return false.
- `x` no longer removes directly; it opens the confirmation (or the built-in
  error message from point 1).
- `render()`: while the confirmation is open, render the question and the two
  answers instead of the normal footer. Question text: `remove <id> from this
  board?` for a board lane, `delete <path>?` for a catalogue file. Answers
  rendered `no` first, then `yes`; the selected one with `stySelected`
  (view.go:35), the other with `styMeta`. Footer line while confirming:
  `←/→ choose · enter confirm · esc cancel` (wrapped through the existing
  `wrapHints`/`styMeta` treatment like the normal footer).
