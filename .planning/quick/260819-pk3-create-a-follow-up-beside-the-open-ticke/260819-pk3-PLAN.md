# Quick Task: write a follow-up next to the ticket it is for

## The ask

From an open ticket, `n` starts a follow-up without going back to the board. The
screen splits: the ticket you are on stays on the left, the follow-up is written
on the right, so the reason for it is still visible while it is written. Which
pane is active is visible, `tab` moves between them. The follow-up can be
cancelled unsaved. Once saved it stops looking editable and reads as a normal
ticket, still beside its predecessor, with the same keys a single open ticket
has. `n` again chains: the ticket you just wrote slides left and a new follow-up
opens on the right. The follow-up lands in the backlog. Under ~80 columns there
is no split — the follow-up takes the screen.

## Established facts (read in the code this session — do not re-investigate)

- `followUp()` (`internal/tui/signoff.go:154-193`) **already** creates a
  follow-up: default lane, `follows: <src id>`, assignee inherited,
  `followUpContext(src)` as the context prose, and a body seeded with a
  `## Definition of Done` checklist. It then replaces `m.detail` with the new
  ticket and opens the field editor. It is reachable only as `f` at a human
  checkpoint (`model.go:786-789`, `atHumanCheckpoint` at `signoff.go:197-203`).
  This task reuses its field-building, and leaves the `f` path alone.
- `followUpContext`'s first line is "Raised from the review of X."
  (`signoff.go:134`), asserted by `signoff_test.go:138`. A follow-up started from
  any lane needs a different lead-in, so the lead-in becomes a parameter and the
  sign-off path keeps its wording and its test.
- **The field editor writes per field, straight to disk**: `commitEdit()`
  (`edit.go:43-73`) runs `store.Mutate` on tab/ctrl+s. There is no draft concept
  today, so "cancelled and not saved" cannot be done by editing a created ticket
  — the ticket must not exist until the follow-up is saved. `editableFields`
  (`edit.go:17-29`) is the field list; `renderEdit` (`edit.go:125-173`) reads
  values through `f.get(m.detail)`.
- `renderDetail` (`view.go:587-693`) is one function that both builds the body
  and, at the end, hands it to `clipToWindow` (`view.go:703-741`) which owns the
  footer and `m.detailScroll`. It reads `m.width` in eight places. Rendering it
  into a pane means splitting body-building from clipping.
- `View()` (`view.go:63-92`) dispatches `modeDetail` → `renderSignOff` when
  `atHumanCheckpoint()`, else `renderDetail`; `modeEdit` → `renderEdit`.
- `n` is **free** in `modeDetail` (`model.go:786-853` binds esc/q/enter, e, E, a,
  f, y, m, b, arrows, paging, j, k — no n). `tab` is free there too.
- `tab` and `shift+tab` are **taken** in `modeEdit`: next/previous field
  (`edit.go:92-101`). So while the follow-up is being written the editor keeps
  tab, and the left pane scrolls with shift+arrows; `tab` moves between panes
  once the follow-up is saved and the right pane is a ticket again.
- `m.detail` is the open ticket, `m.detailFrom` the view to go back to,
  `m.detailScroll` its scroll (`model.go:71-84`). `stySelected` renders a `▌`
  marker (`view.go` styles); `styMeta` is the dim style; `lipgloss.JoinHorizontal`
  is used at `lanes.go:723` and `pipeline.go:231`.
- `m.lanes.Default()` is the lane `createTicket` uses (`model.go:1055+`).
- Baseline green at 391f642: `go build ./...`, `go test ./... -race`,
  `gofmt -l internal/tui/` empty.

## Shape

`m.detail` stays the **right** pane, so every existing detail key keeps acting
on the ticket being worked. A new `follow` struct holds the left pane and, while
it is being written, the draft:

- `src` — the ticket the follow-up follows: the left pane.
- `srcScroll` — its own scroll, seeded from `m.detailScroll` so the source keeps
  the position it was read at.
- `draft` — the field values not yet on disk. Non-nil ⇒ the right pane is the
  editor; nil ⇒ the right pane is `m.detail`, a real ticket.
- `focusLeft` — which pane the plain scroll keys move.

No new mode: drafting is `modeEdit`, a saved follow-up is `modeDetail`, and the
renderer splits when `m.follow != nil`. Focus decides scrolling only; the action
keys always belong to the ticket being worked, which is what the footer says.
