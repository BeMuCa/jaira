<objective>
The settings screen can take a lane from the catalogue into the project (`u`),
publish one to teammates (`p`) and adopt a teammate's (`a`), and the launcher can
set the default board (`d`). **None of those exist as commands** — verified: the
real subcommand list is `path`, `shared`, `show`, `template` and nothing else.

So an agent can find where a lane belongs, print a skeleton and write the file,
and then cannot do anything with it. The `lanes` help even describes the by-hand
loop as needing no TUI, while the step that puts a lane to use is TUI-only.

The logic is already in `core/lane` and already tested — `Export` (share.go:80),
`Publish` (share.go:88), `Adopt` (share.go:96), `SaveDefaultBoard`
(defaultboard.go:86). The TUI's `use`/`publish`/`adopt` (internal/tui/lanes.go:155,
170, 212) are thin wrappers. The commands must wrap the same functions, not
reimplement them.

Second, smaller thing: creating a lane means knowing that `jaira lanes template`
exists, which nothing in the TUI says. Give the settings screen a key that writes
the skeleton and opens it.
</objective>

<task type="auto">
  <name>Task 1: use, publish and adopt as commands</name>
  <files>internal/cli/lanes.go, internal/cli/lanes_test.go</files>
  <action>
Add three subcommands under `jaira lanes`, each a thin wrapper over the core
function the TUI already calls:

- `jaira lanes use <id>` — copy a catalogue lane into this project's
  `.jaira/lanes/`. Wraps `Export`.
- `jaira lanes publish <id>` — copy a lane into `.jaira/shared/<user>/`, stamping
  `creator:` when absent. Wraps `Publish`; the user name comes from the same
  identity function the rest of the CLI uses.
- `jaira lanes adopt <id>` — copy a teammate's shared lane into the catalogue.
  Wraps `Adopt`. Take the same identifier `jaira lanes shared` prints, so the two
  commands compose; if that is a path rather than an id, say so in the help.

Each: `--force` to overwrite (the core functions already take `overwrite`),
`--json` emitting at minimum the written path and what was written, human output
being one plain line naming the file. Refusing to overwrite without `--force` is
the core's behaviour already — surface it as a clear error, not a stack trace.

Tests in internal/cli/lanes_test.go following the existing style: each command
writes the expected file; each refuses an existing file without `--force` and
overwrites with it; `--json` carries the path; an unknown id is a usage error,
not a crash.

<task type="auto">
  <name>Task 2: the default board from the CLI</name>
  <files>internal/cli/lanes.go, internal/cli/lanes_test.go</files>
  <action>
`jaira lanes default` reads the default board; with flags it writes one:

- no flags — print the current default board: which lanes and which ticket
  options a new board starts with, and the path. `--json` for an agent.
- `--lanes a,b,c` — set the lane list
- `--options planning,brainstorm` — set the pre-ticked ticket options
- `--clear` — remove the default board, returning to the built-ins

Wrap `LoadDefaultBoard`/`SaveDefaultBoard`. Reject an unknown lane id or an
unknown option with a usage error naming what is installed — silently writing a
default board that refers to a lane nobody has is how a board ends up empty.

Tests: reading an absent default board prints the built-in state rather than
failing; writing then reading round-trips; an unknown id is refused; `--clear`
removes the file.
