<objective>
Make the `context` field the single place a ticket records why it exists, and make
a multi-line context readable in the file and in a diff.

Three things, in order:

1. **A live read bug, discovered while designing this.** `Doc.Scalar` returns the
   block header token, so a field written as a YAML block scalar reads back as the
   literal string `"|"` (or `">-"` for folded). `Decode` propagates it: a ticket
   with `context: |` decodes to `Context == "|"`, and the promotion gate — which
   only checks non-empty — passes it. This is true in the repository today; the
   README's own example ticket uses `outcome-resolves: >-` and reads back as
   `">-"`. Nothing can be written as a block until this is fixed.
2. **The write side.** Multi-line values become indented block literals instead of
   one long escaped double-quoted line.
3. **One place for the problem.** `## Description` leaves the body template, and
   four (five, counting the skill) places gain real guidance on what makes context
   usable.

Purpose: the file format is the API. A context that is a 400-character quoted line
with `\n` escapes is neither hand-editable nor diff-readable, and a ticket that
answers "why does this exist" in two different places answers it in neither.

Output: block-scalar-aware read/write in `core/ticket`, a body template with one
fewer heading, and consistent guidance in the four registers an author meets.
</objective>

<measured_facts>
These were measured in this repository with a throwaway probe test, not recalled.
Do not re-derive them; do not assume anything beyond them.

Given frontmatter containing:

```
context: |
  first line
  second line

  fourth
outcome-resolves: >-
  folded one
  folded two
goal: after
```

- `d.Scalar("context")` returns `"|"`, ok=true, err=nil. **Wrong.**
- `d.Scalar("outcome-resolves")` returns `">-"`. **Wrong.**
- `d.Scalar("goal")` returns `"after"`. Correct — single-line scalars are fine.
- `Decode` yields `Context == "|"`, `Outcome.Resolves == ">-"`.
- The node type for both is `*ast.LiteralNode` (goccy uses LiteralNode for folded
  scalars too, not a separate FoldedNode).
- `lit.Value.Value` holds the correctly decoded content:
  `"first line\nsecond line\n\nfourth\n"` for the literal,
  `"folded one folded two"` for the folded one.
- `lastLine(node.Value)` returns the **key** line for a LiteralNode, and
  `lastLine(lit.Value)` returns the **first content** line. Neither is the end of
  the block. `lastLine` cannot be used to find a block scalar's extent.
- `d.SetScalar("context", "replaced")` over an existing block returns
  `ticket: "context" uses a multi-line block scalar; not supported by SetScalar`
  (the guard at frontmatter.go:262-264).

Also established before planning:

- jaira never uses a YAML **encoder**. It parses with goccy `ast`/`parser` purely
  as a locator and writes by splicing bytes (`encodeScalar`, frontmatter.go:325).
  goccy encode options are irrelevant here.
- `## Description` in the body template is read by nothing. Lane input is
  assembled only from frontmatter fields named in `input-requires`, resolved by
  `fieldValue` (internal/cli/flow.go:403-432); the markdown body is unreachable
  from there. No gate mentions it.
- `core/ticket/probe_test.go:26` uses the string `"## Description"` as arbitrary
  body filler for a size probe. It does **not** depend on the template.
  **Leave it alone.**
</measured_facts>

  <action>
Add three helpers next to `encodeScalar` and wire them into `NewDoc` and
`SetScalar`. Keep every non-block path byte-for-byte as it is today — this code
writes every ticket file, so the blast radius of a stray reformat is the whole
board.

**`blockable(v string) bool`** — a value gets the block form only if all hold:

1. it contains `\n`;
2. it does **not** end with `\n\n` — two or more trailing newlines need `|+`
   (keep-chomping), whose end is ambiguous to a reader and fragile under
   editors; fall back rather than emit it;
3. no line has a trailing space or tab — block scalars do preserve trailing
   whitespace, but whitespace-trimming editors and pre-commit hooks do not, so a
   block form here would round-trip differently on different machines;
4. no line begins with a space or tab — a first content line that is indented
   requires an explicit indentation indicator (`|2`), which is not worth
   supporting;
5. it contains no `\r` and no control rune below 0x20 other than `\n` — CRLF and
   control characters are not representable in a block scalar without loss.

Anything failing these keeps today's quoted-one-liner path, which is lossless. The
fallback is the correctness guarantee: block form is an improvement in readability,
never a change in what round-trips.

**`renderBlock(key, val, indent, comment string) string`** — returns the entry's
full source lines (no trailing newline), e.g. `context: |` then two-space-indented
content. Rules:

- chomping: value ends with exactly one `\n` -> `|` (clip); value has no trailing
  `\n` -> `|-` (strip). `blockable` has already excluded everything else.
- indentation: the key's own indentation plus two spaces, matching `renderList`'s
  `"\n  - "`.
- blank lines inside the value are written as genuinely empty lines, never as
  lines of indent spaces (that would reintroduce trailing whitespace).
- carry a trailing comment from the key line, as `SetList` does via
  `trailingComment`, appended after the block header. **Prove it re-parses** —
  add a test writing `context: | # from chat` and reading it back. If goccy does
  not accept a comment after the header, keep the comment and fall back to the
  quoted form for that entry rather than dropping the comment.

**`blockExtent(lines []string, start int) int`** — the last source line index an
entry occupies. `lastLine` cannot do this (see measured_facts). Scan forward from
`start+1` while the line is blank **or** its indentation is strictly greater than
the key line's indentation; then walk back off any trailing blank lines so the
frontmatter's own spacing is not swallowed. This is exactly YAML's block-scalar
rule: everything more-indented is content, including a `#` line, while a comment
belonging to the next key sits at that key's indentation and stops the scan. It
also returns `start` unchanged for an ordinary single-line entry, which is what
makes one code path serve both conversions.

**`NewDoc` (schema.go:445-450)** — in the `fields` branch, when
`!rawLiteralFields[k] && blockable(v)`, write `renderBlock(k, v, "", "")`;
otherwise leave the existing `k + ": " + encodeScalar(v)` line exactly as it is.

**`SetScalar` (frontmatter.go:224)** — take the whole-entry path when, and only
when, either `blockable(val)` or the existing node is `*ast.LiteralNode`:

- key absent: `appendBlock(renderBlock(...))` when `blockable(val)`, else the
  existing `appendLine`. (`core/merge` appends `theirs-<field>` keys this way and
  those values can be multi-line.)
- key present: compute `start` from the **key** token's line (not the value
  token's — for a block the value token sits on the header), `end` via
  `blockExtent`, splice `renderBlock` or `key + ": " + encodeScalar(val)` over
  `lines[start:end+1]`, mirroring `SetList`.
- everything else falls through to today's untouched single-line splice, which is
  what preserves quoting style via `encodeScalarLike`.

Delete the now-obsolete "not supported by SetScalar" guard at :262-264 only once
the block path handles that case.

Leave `SetRaw` alone — it is only ever given booleans and RFC3339 timestamps.

**Byte identity is verified by the existing suite.** If any existing test in

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-19h-01 | Tampering | `renderBlock` writing attacker-influenced text into frontmatter | mitigate | `blockable` rejects `\r` and control runes and any line that could break out of the block; anything not provably safe falls back to the existing lossless quoted encoding |

| T-19h-SC | Tampering | npm/pip/cargo installs | n/a | No new dependency; goccy `ast`/`parser` are already in `go.mod` |
